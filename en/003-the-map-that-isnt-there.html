Working with agents — internal note

The map
that isn't there

Why an agent's explanation always convinces you, even when it has misread your project. And what can be done about it.

~8 MIN READ · WITH TWO HANDS-ON TESTS

What it is

Every project has a map

When an agent works on your code it builds an idea of how the thing is put together: what depends on what, who touches which data, what breaks if I change this function. Call it the map.

When it then explains what it did, it is handing you a summary of its map. And there is the whole point, right there: you can only check a summary if you have a map of your own.

The test · 1 of 2

Which one understood?

Two agents were given the same assignment on a small e-commerce app. Read how each one describes the work, then answer.

PROJECT  internal shop · 4 services
ASSIGNMENT  add the loyalty discount to the cart total calculation
AGENT A

I added the discount in CartService.calculateTotal(). I pull the loyalty tier from the user profile and apply the percentage before VAT, so the taxable base stays correct.

I handled the case of a profile with no tier set, which otherwise threw the calculation off. I added two tests on the new branch.

AGENT B

I extended CartService with the loyalty discount. The percentage comes from the user profile and is applied to the taxable base, before VAT.

I defaulted it to zero when the tier is missing, so users without a complete profile don't break. Tests updated.

Which of the two really understood the system?

There was a difference, and it was a big one: the total is calculated in two different places in this project. OrderService recalculates it on its own at confirmation time. Agent A didn't know that, so in production the cart showed the discount and the final order didn't.

That fact was not in the write-up. It was in the map.

Reread the two write-ups knowing it: neither one says it checked where the total gets calculated. One of them had verified it and the other hadn't, but the sentence that tells them apart was never written — because an agent never writes you “I'm assuming this calculation exists in only one place”. It simply proceeds as if that were true.

The mistakes are not in the sentences. They are in what the sentences don't say.

The missing symptom

From the inside everything looks fine

Someone who has the map feels a small strain reading those two write-ups: they have to reconstruct in their head the pieces the text doesn't name. That strain is a signal, and it tells them the account isn't enough — that they need to go and look.

Someone who doesn't have the map feels no strain at all. Not because they understand it better: because there is nothing to reconstruct. That summary is all they have, so nothing strikes them as missing.

The condition erases the symptom that would let you discover it. The feeling of having understood proves nothing.

It is like proofreading a translation from Japanese without knowing Japanese. It will always look perfect — not because it is, but because you have no way of noticing the errors. It reads well, it makes sense, you approve it.

The real problem

It isn't that you don't read the code

It's that the map doesn't exist anywhere.

It isn't in your head. And it isn't in the agent in any stable way either: it rebuilds the map from scratch every time, out of whatever happens to fall under its eyes in that session, and throws it away at the end. A month from now, on the same project, it might build a different one.

Before agents, that knowledge lived in the head of whoever wrote the code. The risk now isn't that it moves somewhere else: it's that it isn't anywhere at all. Nobody accumulates anything.

The objection

“But I don't even know how the compiler works”

A serious objection, and it deserves a serious answer. None of us knows the inner workings of the compiler, the garbage collector, the kernel. Abstraction means exactly this: ignoring what sits behind a boundary.

The difference is that that boundary is stable and documented. The compiler does the same thing tomorrow, a specification exists, and there are millions of people who would notice if it changed. You can afford not to look inside because the boundary holds on its own.

The code the agent generated for you on Tuesday has none of that: no specification, no guarantee that regenerating it produces the same thing, nobody protecting that boundary. It isn't abstraction. It's absence dressed as abstraction.

A warning

And diagrams won't save you

You'd think it would be enough to ask the agent to draw what it does instead of describing it. It helps — but only if you already have a map of your own to compare against. It's for spotting the arrow too many, or the one that's missing.

Without a map, a diagram is the same thing as before, drawn better. And therefore more convincing: a wrong diagram persuades you more than the same mistake written out in words would. It makes the rubber stamp prettier, not better informed.

The test · 2 of 2

Three questions to find out where you stand

Think about the last thing you had an agent do. Answer honestly: nobody is watching.

01 Before you launched it: could you say, even roughly, where the change would land and what else it would touch?
02 After: could you explain out loud to a colleague why the code is the way it is, without rereading it?
03 It breaks in a month: would you know where to start looking?

Waiting for all three answers

This is not a test of skill. It only shows whether the map is there.

What to do

Five questions to ask the agent

The map gets built by asking. These five questions cost ten seconds, and they are the ones senior developers got used to asking themselves back when the only way to get an answer was to go and find it in the code.

Before you start: what do you think this change will touch, beyond the file I'm looking at?

Make your own prediction before reading the answer — wrong is fine, vague is fine. The value is in the gap between the two, and with no prediction there is no gap to see. This is the habit that changes the most.

What did you NOT touch, and why were you confident you could leave it alone?

It forces the agent to state the boundaries it is assuming. That is exactly where the mistakes hide: in the total calculation it thought lived in one place only.

What else in the project uses this?

Always ask before accepting a change to something shared. It is the question that would have saved Agent A.

Why this way and not another? Which alternative did you discard?

The what is already in the diff; reading it narrated back is wasted time. The why is written down nowhere, and it disappears at the end of the session if you don't pull it out.

Which assumption are you making that you haven't verified?

It doesn't always answer well, but when it does it hands you in one line the thing no summary contains.

And now and then, a field test

Predict what breaks if you change a value. Then actually change it and look. It is the fastest way there is to discover your map had a hole — and holes found that way you never forget.

None of this is an advanced technique.

The map is not a reward for seniority: it is the residue of those questions, asked many times over. The only difference today is that you have to remember to ask them, because there is someone ready to answer even when you don't.
