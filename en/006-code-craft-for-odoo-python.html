Engineering guideline · Python / Odoo addons

Your code works. That's the easy half.

The hard half is whether the person who opens that file in eighteen months — statistically: you — can change it without breaking three things they didn't know existed. Odoo work never teaches you that half. The framework does the organising and hands you a place to put code.

Don't read this end to end. It's three separate sessions, in increasing order of what they demand from you. Finish one, go and use it for a fortnight, come back.

Level 1 · Do it now

~15 min · zero theory. Mechanical fixes you can apply to your very next commit without understanding a single new concept. Seven topics.

Level 2 · Build the habit

~25 min · needs judgement. The vocabulary and the trade-offs. Rules with boundaries, which means deciding when they apply. Nine topics.

Level 3 · Go deeper

~25 min · needs practice. Design decisions you'll only really learn by making them badly once. Reading list included. Seven topics.

L1 · Split the file

One model per file. Start today, no thinking required.

# before # after tk_plant_nursery/ tk_plant_nursery/ └── models/ └── models/ ├── __init__.py ├── __init__.py └── models.py ← 900 lines ├── plant_nursery.py ├── plant_order.py ├── plant_order_line.py └── res_partner.py ← extensions keep the CORE name

Finding things

A colleague opens plant_order.py. Not a 900-line scroll.

Merge conflicts

Different files merge automatically. Pays for itself in a month. inferred

Readable history

"What changed in orders?" stops being archaeology.

Length means something

One subject → length is a signal. Nine subjects → noise.

Rule: file named after the model, dots become underscores. Your additions to core models go in a file named after the core model, so anyone hunting partner behaviour finds them without knowing your addon exists. Watch the import order in __init__.py — base models before the ones referencing them.

L1 · Mark what's private

Four keystrokes, three fewer promises

A name without an underscore can be called by another addon, a customer's RPC script, or a consultant's automated action from 2021 — so renaming it is a breaking change. With the underscore, Odoo refuses the RPC call, and renaming takes five minutes. established

Same code. Same behaviour. Four extra underscore characters — and you went from three things you can never safely rename to one.

Here is a rule your monkey brain can follow without thinking: start every method with an underscore, and delete the underscore only when you can name the specific outside caller that needs it. Default to closed. Opening is free. Closing is a breaking change, an apology, and a customer call at an inconvenient hour.

L1 · Flatten the control flow

Guard clauses, not nesting

The mechanical move: invert each condition, raise immediately, unindent everything else. The valid path falls out at the bottom.

Adding a fifth rule: left — find the right nesting depth and add another else in the correct place. Right — add two lines anywhere in the list. That difference is maintainability; it isn't a virtue, it's how long the next ticket takes.

L1 · Flatten the control flow

Two traps with one-character fixes

If a flag makes the function do two genuinely different things, it isn't a parameter — it's two functions in a trench coat. Split them.  ·  The second trap is caught automatically by your linter (B006) — but learn the mechanism, because "runs once at import" explains several other Python surprises you'll meet later.

L1 · Extract & assert

A comment above a block is that block asking to be a function

You already did the hard part — you identified a chunk with one purpose and named it in English. Promote the comment to a method name and the comment disappears, because the code now says it.

Steps: select the block → variables it reads become parameters, what it produces becomes the return → cut into _verb_noun() → replace with the call → run it.  ·  "Isn't jumping to another method harder to read?" For a two-line method with a bad name, yes. For a fifteen-line block with a good name, no — most readers don't want the details at all, and that reader is the common case.

L1 · Extract & assert

self is a collection. Say how many you expect.

In Odoo, self is never one record. It's a recordset holding zero, one, or five thousand — and the same method gets called with all three, from code you didn't write.

ensure_one() is not defensive clutter. It is documentation the computer checks: it tells the next reader what the method assumes, and turns a confusing failure deep in the stack into a clear one at the entrance.

L1 · Don't break the chain

Always call super(). Always return what it gave you.

No super()

You silently delete every other addon's behaviour — including core Odoo's. The bug report arrives weeks later from a different feature and looks unrelated.

No return

Callers get None. It breaks far away from your file, and nobody will connect it to you.

Assignment vs setdefault

vals['code'] = ... overwrites whatever the caller passed. setdefault fills in only when it's missing. One of these breaks a data import.

version @api.model_create_multi with a vals_list is required on modern versions. Old single-vals examples you'll find online are deprecated. Why the chain exists is a Level 3 topic — for now, just always do both.

L2 · How code drifts

Nobody decided to write a 900-line file

Every single step was locally reasonable. That is exactly why explicit rules are needed — good local judgement, applied repeatedly, reliably produces this. There is never a ticket called "reorganise the file": no visible business value, first thing cut from the sprint.

Technical debt
The accumulated cost of choices that were fast to make and are slow to live with. Small amounts are a legitimate tool. The problem is the interest: every future change in that area costs more, forever, until someone pays the principal. Debt taken deliberately and written down is a decision. Debt taken by accident is a leak.
L2 · How code drifts

Four forces pushing you there

Framework owns the entry points

You never write the starting point — you write methods Odoo calls. Nothing in your code ever assembles anything, so assembling never becomes a habit you have.

The model is a magnet

self gives you the record, cursor, user, context and every other model. All logic is reachable from the model, so all logic ends up on it.

Nothing fails at build time

A 200-line method compiles fine. Feedback arrives eight months later as an incident nobody connects to the cause. Late consequences don't teach.

You learned from core addons

15 years of patches written under Odoo's own rule: never restructure a stable file, keep diffs minimal. established

Read core addons to learn how the framework works. Do not read them to learn how code should look — you'd be copying a style produced by a constraint that does not apply to you.

L2 · How code drifts

Two words that name the entire problem

Target, always: low coupling, high cohesion. Nearly every rule in this deck is one of those two in a costume. When you can't remember why a rule exists, ask which one it protects — that question answers most of Level 2 on its own.

L2 · Encapsulation

Level 1 gave you the underscore. Here's what it's actually for.

Encapsulation
Deciding on purpose which parts of your code the outside world may depend on, and keeping that set as small as you can get away with. The smaller the promised surface, the more freely everything behind it can change. Not secrecy — freedom. Most useful idea in this deck.

L2 · Abstraction & contracts

One level of abstraction per function

A function either orchestrates named steps or performs one step. Never both. When you see self._notify_partner() two lines from string concatenation — that's the yank. Extract.

Abstraction
Choosing a level of detail and staying on it. A good one lets you use something correctly without knowing its internals — you drive without knowing about fuel injection. A leaky one makes you learn the internals anyway, so it bought you nothing.
L2 · Abstraction & contracts

Docstrings state the contract, not the name

The test: could someone call this correctly having read only the docstring? Write what the caller cannot see from the signature — preconditions, what it raises, what it changes, units. Everything else is noise, and noise trains people to skip docstrings entirely.

L2 · Abstraction & contracts

Smoke alarms, not laws

Cross one and you don't automatically have a problem — you have a question to answer in the PR description. Numbers chosen to be slightly uncomfortable rather than optimal. untested

25lines in a function → justify or extract
3levels of nesting → guard clauses
300lines in a model → a service is hiding in there
4parameters → some of them are one object

And the fifth: the same 3 lines in 3 places. Extract them, then decide where the extracted thing lives.

But note carefully — duplication is a signal, not automatically a sin. Two blocks that look identical today but will change for different reasons should stay separate; merging them creates coupling between two things that have nothing to do with each other. Extract when they change together. This is your first real judgement call.

L2 · The services layer

The boundary — where this stops paying

The test: could a business person state this rule without mentioning Odoo?

Yes → move it to services/

pricing rules · VAT · discount tiers · scheduling · file parsing · external API payloads · date arithmetic

No → leave it on the model

setting a state field · posting to chatter · building a search domain · creating related records · anything fundamentally an ORM operation

Watch carefully, because here is where a freshly-educated monkey brain reliably goes wrong. You have just learned a Powerful Concept, the concept feels good, and so you will want to apply it to everything. Within a week you will have services/state_setter.py. Congratulations: you have reinvented the model layer, only slower and with more files.

The mark of an actual engineer is not knowing a technique. It is knowing the technique's boundary — the exact conditions under which it stops paying and starts costing. Every rule in this level has one. Learn the boundaries with the same energy you learn the rules, or you will simply generate a more sophisticated grade of mess.

L2 · Refactoring discipline

Refactoring = structure changes, behaviour doesn't

Not "improving it". Not "rewriting while I'm in there". Structure only. The definition sounds pedantic and is entirely load-bearing.

Code smell
A surface symptom that often — not always — indicates a deeper problem. "Smell", not "bug": the code works. It's the software equivalent of a noise from the engine. You investigate; sometimes it's nothing.
L2 · Refactoring discipline

Four named moves you'll use weekly

Replace Temp with Query

Smell: a variable set at the top, used 40 lines later. Long-lived temps are the invisible reason long functions stay long — you try to extract and find the block needs three temps computed elsewhere, so you give up. Kill the temps first: this is a preparatory move, its job is to make other moves possible.

Split Loop

Smell: one loop accumulating four unrelated things. Split it: one loop, one job, each extractable. "But it iterates four times!" — yes, and it doesn't matter, the data is in memory. Exception: if the loop body touches the database, don't split — batch.

L2 · Queries & recordsets

N+1: the loop that queries

Spot it without profiling: for every loop, ask "does anything in here talk to the database?" — search, create, write, unlink, or reading a relational field on records not fetched together.  version the grouping API changed shape across recent releases; copy the signature from a core addon in your source tree, not from a blog post.

L2 · Tests

Tests are what make refactoring legal

Permission to change

The real reason people fear that 900-line file is that they can't tell whether they broke it. Tests answer in seconds — fear becomes a task.

Documentation that can't rot

Comments lie eventually. A test that lies fails.

A named specification

L2 · Tests

Team rule: a bug fix ships with a test that fails before the fix. Sounds like extra work; usually isn't. The failing test gives you a one-command reproduction, so you stop clicking through the UI to check yourself — and it's the only thing that stops the bug returning in eight months.

The interesting cases — exactly 50 units, zero, a negative price — are the ones nobody writes when each test costs a database fixture. At a millisecond each you write fifteen and find two bugs you weren't looking for.

L2 · Gates & checklist

Add the complexity gate — slowly

What C90 counts: the number of independent paths through a function — roughly one, plus every if, elif, for, while, and, or.

A decent proxy for "how many cases must a reader hold in their head", and an excellent one for "how many tests would cover this properly". When it complains, the fix is almost always guard clauses or extraction.

Ratchet, don't big-bang. Set it just above today's worst function, then lower by one whenever CI is green. A gate that fails 400 times on day one gets switched off on day two — and then you have no gate and a demoralised team. inferred

L2 · Gates & checklist

The daily artifact tap an item to tick it

0 / 15 checked
  • Can I name what each method does in one sentence? If the sentence needs "and", it does two things
  • Is every non-API method prefixed with _? Public names are promises to strangers
  • Does any method both decide and execute? Separate the rule from the action
  • Is there business logic that could live in services/? Rules a business person could state
  • Any query inside a loop? search, create, write, or a relational read on unfetched records
  • Does every single-record method start with ensure_one()?
  • Do the @api.depends lists match what the compute actually reads? Including through relations
  • Does every override call super() and return its result?
  • Is this override the cheapest mechanism? Could it be a default, a compute, or a constraint?
  • Is sudo() scoped to one expression, with a comment saying why?
  • Are user-facing strings wrapped in _()? And the lazy variant at class level
  • A new if/elif on an existing Selection field? Check whether that ladder exists elsewhere
  • Is there a test that fails without this change?
  • Are refactoring commits separate from behaviour commits? A mixed diff can't be reviewed

Run it on your own PR before requesting review. That's where the learning happens — you catch your own patterns. And a comment on your code is not a comment on you: the reviewer is the first person to read what you wrote, which makes them a free usability test on your own thinking. If they misunderstood, the code was ambiguous. That's data, and it's the cheapest you'll ever get.

L3 · Composition vs inheritance

"is a" versus "has a"

"Prefer composition over inheritance" is not fashion. Inheritance couples you to the parent's internals, not just its interface — and in Odoo the parent is maintained by someone else, on their release schedule. That's why, of the four mechanisms in Level 2, the mixin is the one to reach for when you're unsure.

L3 · Composition vs inheritance

What super() actually does

Level 1 told you to always call it and always return it. This is why: you're not overriding a method, you're inserting a link into a chain assembled at runtime from code you have never read, whose order changes per deployment.

Consequence worth sitting with: your override must work correctly no matter what runs before or after it. That's the real argument for keeping overrides tiny and delegating immediately to a private method of your own.

L3 · Polymorphism

Replace Conditional with Polymorphism smell: the same if/elif in several methods

Odoo is full of Selection fields, and every selection eventually grows a matching ladder in five methods. Add an option, find all five. Miss one → a bug that only appears for that option, which QA never hits.

Polymorphism, plainly: instead of the caller asking "which kind is this?" and branching, each kind gets a small class offering the same method name. The type does the choosing. This is the technique Level 2 kept deferring to.

L3 · Polymorphism

The payoff, stated as a diff

abc.ABC does real work here: forget send() in a new channel and the class cannot be created at all. The mistake surfaces at import, not in production at 2am. established

The boundary: this costs indirection — the reader has to jump to another file. With two branches that never change, the plain if is better. Apply when the ladder appears in more than one method, or when the third option arrives. Two is a coincidence; three is a pattern.

L3 · Bigger surgery

Extract Class smell: a group of methods only touches a group of fields

Open a large model and check which fields each method uses. If eight methods only touch five fields, and the other twenty never touch those five — that's two classes sharing a file by accident. Low cohesion, made measurable.

Destination 1 · service class

Plain Python in services/. Cheapest. Correct when the extracted thing is rules.

Destination 2 · AbstractModel mixin

When it needs the ORM and is reused by several models.

Destination 3 · new model

Most expensive — a table, views, access rules. Only when the thing has its own identity and lifetime in the database.

The steps, and the order matters more than the destination:

name the concept → create the new class → move one method → make the old method delegate to the new one → run tests → repeat → delete the delegating methods once nothing calls them.

At no point is the system broken. If you're interrupted for three days, what's on the branch still works and can still be merged. That property is the whole technique — everything else is bookkeeping.

L3 · Bigger surgery

Strangler: changing code you're afraid of

Both instincts are wrong: leaving it alone forever is slow decay; the heroic weekend rewrite is an unreviewable diff carrying every bug you introduced plus every undocumented behaviour you didn't know it had. established — a documented industrial technique, not our invention.

L3 · Bigger surgery

What every move in this deck has in common

Small

Each fits in one sitting. None requires holding the whole system in your head — which, per the introduction, you cannot do anyway.

Verifiable

Tests green after each one. You always know whether you're still standing on solid ground.

Reversible

Interrupted for three days? What's on the branch still works. git revert is always available.

The heroic weekend rewrite feels like engineering because it feels hard, and your monkey brain has an unfortunate habit of mistaking effort for value. It is not engineering. It is a bet, placed with your team's uptime, by someone who confused adrenaline with competence.

Real engineering is boring on purpose: ten dull steps, each verified, arriving somewhere you could not have jumped to. If your refactor is exciting, stop — you've made the steps too big.

L3 · Design patterns

A pattern is a name, not a technology

Someone noticed the same shape appearing in thousands of programs, wrote it down, and gave it a name so people could discuss it in three words instead of thirty. That's the whole idea — and it means you have already invented several by accident.

L3 · Design patterns

Four we do not want to see here

DI containers

Python has module imports and default arguments. A container adds configuration and indirection to solve a problem you don't have.

Repository layer over the ORM

The ORM is the repository. Wrapping it gives you a second, worse ORM to maintain.

Singleton classes

A Python module is already a singleton. Just use a module.

Do-nothing getters/setters

get_name() returning self.name is ceremony. Use the plain attribute — promote to @property the day it needs behaviour, and no caller changes.

A warning about what happens next, and I say this with the deepest affection for your species. Roughly three days after learning the word "pattern", a monkey brain enters a phase where everything is a pattern opportunity. Factories producing factories. An interface with exactly one implementation, "for flexibility". Six files where there was a function.

The tell is that it feels sophisticated. Actual sophistication looks like this: someone reads your code, understands it immediately, and does not notice anything clever happened. If a reader has to admire your design before they can use it, you didn't build them a tool — you built yourself a monument, and now they have to dust it forever.

L3 · ORM depth

Three where the cost is correctness, not speed

@api.depends

Must list every field the compute reads, including through relations. Miss one → a stale value, only under certain edit orders, only sometimes. The hardest bug class on this page to reproduce — which is why it's here rather than in Level 1. established

sudo()

Disables access rights. Scope it to one expression, never a whole method, and never to a search whose domain contains user input — that's how you build a data leak by accident. Every use gets a comment saying why.

Raw SQL

Needs written justification in the PR, and always parameterised: cr.execute(q, (a, b)), never an f-string. It skips caches, record rules and computed fields. Sometimes exactly what you want — never what you want by accident.

What links all three: the ORM is doing enormous amounts of work on your behalf — dependency tracking, permission filtering, caching, batching. Each of these three steps outside that machinery, and the failure mode is never a crash. It's quietly wrong data, discovered by an accountant, in a quarter's time.

The general principle worth taking away: when you bypass a framework's guarantees, you inherit the responsibility for them. Write down which one you took on, in the PR, where the next person will see it.

L3 · Why any of this works

The real reason to write tests

I am aware that "write tests" lands on a busy monkey brain as "do extra work for no visible reward", and that when the deadline arrives the tests are the first thing thrown overboard. So let me reframe it in terms your survival instinct will actually process.

Tests are not a tax on shipping. Tests are the mechanism by which you stop being afraid of your own code.

Every developer you have ever met who seemed unreasonably fast at changing complex systems was not smarter than you. I have met smarter, and they were not it. They simply had a way to check their work in under ten seconds — so they tried six things in the time it took you to work up the courage to try one.

Which is the thread running through all three levels: every technique here converts fear into a procedure. Split the file so you can find things. Underscore it so you can rename it. Extract it so you can test it. Test it so you can change it. Strangle it so you can replace it without betting the quarter.

L3 · Keep going

Four weeks. Each step makes the next one easier.

Then, ongoing: run the Level 2 checklist on every PR, starting with your own. Reviewing is where pattern recognition actually forms — you're seeing the consequences of choices instead of making them.

You will not absorb this by reading it. Nobody does. Reading produces the feeling of understanding, which is a different substance from the ability to do it on a Thursday under pressure.

L3 · Keep going

What to read, in this order

1 · Refactoring — Martin Fowler (2nd ed.)

The catalogue that named most of the moves here. Read the first three chapters properly, then use the rest as a lookup. Examples are in JavaScript; they translate without difficulty.

2 · A Philosophy of Software Design — Ousterhout

Short and opinionated. The best available treatment of where to draw boundaries: deep modules, narrow interfaces. Read it second — it changes how you read Fowler.

3 · Odoo Coding Guidelines

The official page for naming, layout and ORM idioms, plus the OCA contributing guide for shared repositories.

4 · Your own Odoo source tree

addons/sale and addons/account, to learn how the framework wants to be extended. Reference material — not a style model, for the reason given in Level 2.

Deliberately not covered: XML and OWL frontend conventions · security and access-rule design · migrating modules between Odoo versions · performance profiling. Each deserves its own deck rather than a paragraph in someone else's.

L3 · Keep going

One last thing

Everything in these three levels is a technique for working around a brain that holds four things at once, forgets its own decisions within weeks, and reliably mistakes familiarity for understanding.

That is not an insult. It is the design spec you are working with. It is the same one every great engineer in history worked with, and the great ones were simply the people who stopped arguing with it and started building around it.

The developers you think are brilliant are not holding more in their heads than you are. They just spent years accumulating small habits so that they don't have to. You have now been handed a list of those habits in about an hour, which frankly is a considerable head start, and I expect you to be appropriately grateful.

Go split a file.
